Special Feature Cards (Technical Deep-Dive)
Interactive “No” Button (Proposal): The distinguishing gimmick is the NO button that cannot be clicked easily【12†L29-L34】. Implementation: A frontend script moves the NO button’s position whenever the user’s cursor (or finger) approaches. For example, on mouseover/touch events detect proximity and randomly shift the button’s CSS left/top. No API calls needed. The YES button remains stationary. When YES is finally clicked, the UI plays a success animation. Backend: None (all logic on client). Just store the question and names in a database for rendering. Security: This is trivial fun; no sensitive data is exposed beyond what user enters. Scalability: No load beyond serving the static page.
Scrambled Photo Puzzle: Implements a jigsaw on a photo. Process: When the sender uploads a photo, save it (e.g. to cloud storage) and record the URL. Then either pre-generate the puzzle pieces on the server or (more efficiently) do it client-side: load the image into an HTML5 canvas, divide it into a grid of N×N tiles, and render each tile as a draggable element with a random initial offset. The recipient can drag tiles to solve. Optionally, track if solved. APIs/Libs: No external API needed; use Canvas or a JS library for drag-and-drop (e.g. interact.js). Data: Store image path and any hidden message text in your DB (table puzzles). No need to store puzzle state – it’s generated on each view. Storage: Images in S3 or similar; DB row for metadata. Security: Sanitize image content and use expiring URLs for storage. Scalability: Image handling on upload scales like any file upload (use load balancer/auto-scaling if heavy). Client-side puzzle solves mean almost no backend compute on play.
Interactive Birthday Animations: Key interactions: Balloon popping and Candle blowing【34†L210-L219】【34†L221-L230】. Implementation: Place several absolutely-positioned balloon elements (images or SVGs) that float up via CSS animation. Each is a button; on click, play a confetti effect (e.g. using a canvas confetti script) and remove the balloon DOM element. Only when all are popped do we proceed. For candles: display flame images on top of cake; on each tap, replace a lit candle with an unlit graphic until all are gone. After all interactions, transition to the letter view. APIs: None beyond basic web APIs; possibly use the Web Audio API to play a birthday music clip (user must click to start audio). Data: The recipient’s name is rendered on the cake (via canvas text). Security/Scaling: Pure frontend. Backend only needs to supply the name/letter from birthdays table. Animations and audio run client-side.
Friendship Day Mini-Games: This feature bundle includes:

•	Friendship Contract: A final screen depicting a signed contract. Could animate checkmarks or signatures. Implementation: Simple DOM/CSS animation (e.g. line drawing with SVG).
APIs/Algorithms: All of the above are implemented in JavaScript/CSS. The only “algorithmic” part is generating the word search grid. All user data (names, traits, the photo URL) are retrieved from the DB. Data: Save the list of “bond traits” and the one-line message so it can appear in the narrative text. Technical Stack & Integrations
While the exact tech stack isn’t published, evidence points to a modern JavaScript stack:
•	Frontend: Likely a React-based single-page app (social media hints suggest “built with React.js”), with separate routes for each card. The static pages (descriptions, FAQs) might be server-side rendered for SEO. UI components include file upload controls (for photos), animated canvases, and CSS effects. The presence of drag-and-drop areas (e.g. puzzle, QR upload) implies libraries like Dropzone or custom handlers. Animation libraries (like GSAP or Canvas for confetti) might be used.
•	Backend: A REST API server (likely Node.js/Express or similar) handles data storage and payments. Each template creation probably hits endpoints like POST /api/proposals, POST /api/birthdays, etc. These endpoints would validate input, possibly generate a unique short code (UUID or hash) for the link, and save the record in a database. On success they return the share URL (e.g. /valentine/s/{code}). The server also needs an endpoint to verify Razorpay payments (Razorpay’s webhook or callback) and only finalize creation after payment is successful.
•	Database: Could be a relational DB (MySQL/PostgreSQL) or document DB (MongoDB). Example schema (SQL style) for birthdays:

 	CREATE TABLE birthdays (
  id VARCHAR(8) PRIMARY KEY,
  recipient_name TEXT,
  birth_date DATE,
  style VARCHAR(50),
  letter TEXT,
  created_at DATETIME
);

// Word search generation (friendship card)
function generateWordSearch(wordList) {
  const size = 8;
  let grid = Array.from({length: size}, () => Array(size).fill(''));
  // Place words in grid (horizontal only for simplicity)
  for (const word of wordList) {
    const row = getRandomInt(0, size);
    const col = getRandomInt(0, size - word.length);
    for (let i = 0; i < word.length; i++) {
      grid[row][col + i] = word[i];
    }
  }
  // Fill empty cells with random letters
  for (let r = 0; r < size; r++) {
    for (let c = 0; c < size; c++) {
      if (!grid[r][c]) {
        grid[r][c] = String.fromCharCode(65 + getRandomInt(0,25));
      }
    }
  }
  return grid;
}
